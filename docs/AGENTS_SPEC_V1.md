# AI Super Console：Codex 多 Agent 协作开发总规范 V1.0

> 用途：本文件直接放入代码仓库，作为 Codex 主控 Agent 和所有专业 Agent 的共同开发规则。

## 开发目标与基本原则

- 开发目标：让多个 Codex Agent 在同一个代码仓库中并行开发 AI Super Console，减少代码冲突、接口不兼容、重复开发和未经验证的交付。
- 基本原则：主控统一决策，专业 Agent 按边界执行，所有模块遵守共同契约，测试结果决定是否通过。

## 一、组织架构

- 产品负责人（用户）：产品方向和重大决策的最终负责人；主控 Agent 是工程协调负责人。
- 主控不能擅自改变产品核心目标，也不能把未通过测试的代码宣布为完成。
- 专业 Agent 不得一开始就自由修改整个项目，必须按任务范围和文件所有权工作。

## 二、七个 Agent 的责任边界

### Agent 0：主控与架构负责人
- 职责：审查仓库、维护架构与依赖、定义数据模型/API 契约/错误规范、拆解可验收任务、指定唯一负责人、协调依赖与并行、审查交付、组织集成测试与发布。
- 可修改：架构文档、任务清单、模块依赖、经批准的公共契约、集成与构建配置。
- 不应：未经评估重写项目、随意改专业模块实现、接口变更不通知、把自述当测试证据、绕过安全门禁。
- 交付物：架构文档、任务依赖图、接口契约、集成记录、阶段验收报告。

### Agent 1：后端与数据库负责人
- 范围：工作空间数据隔离、表结构与迁移、面板/任务/经理人/工作流持久化、REST API、输入校验与统一错误、数据一致性与并发控制。
- 不负责：决定主脑规划策略、自行扩大授权范围、改前端、绕过工作流直接执行长任务。
- 验收：迁移可执行、API 契约一致、隔离测试通过、异常输入正确处理。

### Agent 2：前端与动态面板负责人
- 范围：主控制台、面板布局与组件渲染、面板创建/编辑/停用/恢复、语音与文字入口、任务状态与错误展示、面板版本与运行状态。
- 第一版动态面板必须通过「受约束 JSON 配置 + 审核过的组件库」生成；禁止把 AI 输出的任意脚本直接当前端代码执行。
- 不负责：改数据库、自行决定业务权限、直连未授权外部 API、用模拟数据冒充真实数据。
- 验收：配置正确渲染；无效配置报错；加载/空/失败/无权限均有界面。

### Agent 3：AI 主脑与经理人负责人
- 范围：模型调用抽象、意图识别、任务规划与结构化输出、经理人配置与运行时、任务交接、上下文与工作记忆、结果汇总与可解释报告。
- 硬规则：主脑只能提出计划，不能自赋权限；经理人只能使用当前授权允许的工具；对结构化计划必须校验格式、参数、依赖、权限。
- 不负责：绕过权限、直连生产库、把计划执行结果伪装成真实结果、自行决定资金最终授权。
- 验收：需求→符合契约的计划；无效输出被拒绝；未授权操作无法通过工具层执行。

### Agent 4：工作流与工具连接负责人
- 范围：定时与事件触发、调度与状态管理、工具注册与适配器、超时/重试/幂等/取消、外部连接、结果验证、重启恢复。
- 硬规则：工作流执行与模型推理分离；模型只建议下一步，是否开始/重试/成功由确定性程序判断；超时不得直接判定失败并重复提交。
- 不负责：决定谁有权调用工具、绕过安全模块、把网络超时一律当可重试。
- 验收：定时可执行、状态可查、重复受控、失败符合策略、重启可恢复。

### Agent 5：安全与权限负责人
- 范围：认证与会话、租户隔离、策略权限、工具授权、高风险确认、密钥保护、提示注入与越权测试、安全审计与应急。
- 拥有独立安全阻断权：发现违反已批准安全策略可阻止进入验收；跨模块修复应创建任务由对应负责人实施。
- 验收：越权被拒、隔离有效、敏感工具遵循授权、审计完整、密钥不进入日志或模型提示。

### Agent 6：测试与质量保障负责人
- 范围：单元、API 契约、集成、端到端、权限与安全、异常注入、回归、发布验收报告。
- 不得只验证正常路径；不得单方面改业务实现让测试通过。
- 验收：所有关键测试有实际执行结果、可追踪记录、明确通过标准。

## 三、代码所有权（避免互相覆盖）

| 内容 | 主要负责人 | 修改规则 |
| --- | --- | --- |
| 总体架构与任务清单 | 主控 | 变更需记录原因和影响 |
| 后端业务实现 | Agent 1 | 其他 Agent 通过接口协作 |
| 前端与面板组件 | Agent 2 | 后端变更通过契约同步 |
| AI 主脑与经理人 | Agent 3 | 工具调用遵守统一协议 |
| 工作流与连接器 | Agent 4 | 外部操作经过安全检查 |
| 权限与安全策略 | Agent 5 | 高风险变更必须审查 |
| 自动化测试 | Agent 6 | 测试结果必须可复现 |
| 公共数据契约 | 主控维护，相关人评审 | 修改前评估影响并通知依赖方 |

- 支持独立工作树/分支时，每个专业 Agent 用独立工作区，经受控合并进入主分支；不支持时串行改共享文件、并行做互不冲突任务。
- 不得假设 Codex 一定支持某种多 Agent 能力；实施前先检查版本与运行模式。

## 四、统一任务交接格式（任务契约）

- 每个任务包含：`task_id / title / owner / reviewer / goal / inputs / outputs / dependencies / allowed_paths / forbidden_actions / acceptance_criteria / completion_requirements`。
- 完成时必须报告：改了什么、新增哪些文件、执行了哪些测试、通过/失败、是否越界改文件、已知问题、需要谁接手。
- 禁止只提交一句「开发完成」。

## 五、开发执行链路（阶段门禁）

- A 审查：先读仓库结构、代码、依赖、测试、配置、运行说明；不得未检查就重建骨架。
- B 契约冻结：先定接口、数据结构、错误码、权限；修改需影响分析与记录。
- C 并行开发：只并行无未解决依赖的任务；可用契约 + 模拟服务先行，但模拟成功不等于真实集成成功。
- D 集成：合并前检查变更范围、格式、静态检查、单测、接口兼容。
- E 验收：在真实集成环境跑测试；外部服务在测试环境验证真实连接与结果。
- F 发布：达到验收标准才进入下一阶段；关键安全测试失败则不得发布该安全边界功能。

## 六、安全门禁（四级操作分类）

| 等级 | 操作类型 | 执行规则 |
| --- | --- | --- |
| R0 | 读公开信息、生成草稿 | 按已授予权限执行 |
| R1 | 读用户授权业务数据 | 验证身份、数据范围、权限 |
| R2 | 改业务记录、发外部消息、删数据 | 按风险策略确认/审批，留审计 |
| R3 | 转账、资金授权、不可逆/高影响 | 专门授权、明确确认、严格验证 |

- 所有 Agent 不得自行降低风险等级。
- 模型不得生成/读取不应访问的密钥；用户拒绝后不得换 Agent 重试同一操作；网络超时不得自动判定失败；不可逆操作不得承诺可回滚；无法自动恢复时停止、留证、通知用户；安全日志不得记录助记词/私钥/访问令牌。

| 任务 | 负责人 | 优先级 | 前置 |

## 八、第一阶段验收标准

以一条完整业务链是否真正跑通为准：用户输入需求 → 主脑生成结构化计划 → 创建面板草稿 → 校验配置 → 连接授权数据源 → 经理人执行任务 → 验证结果 → 保存记录 → 用户查看结果。

至少验证：
1. 正常链路可执行；2. 无效面板配置不能启用；3. 未授权访问被拒；4. AI 输出异常不盲目执行；5. 工具失败时状态与错误正确；6. 外部超时不未经核查重复执行；7. 面板更新失败旧版本仍可用；8. 重启后任务可恢复；9. 关键操作有可追踪记录；10. 测试报告与实际运行一致。

## 九、主控启动指令

- 第一项任务不是大量写代码，而是审查仓库（功能/缺失/技术债/依赖/环境）。
- 建立工程规范：总体架构、模块边界、数据模型、API 契约、状态机、权限、错误处理、任务交接、自动化验收。
- 拆解为有明确输入/输出/负责人/依赖/允许修改范围/验收条件的任务。
- 并行独立任务，禁止多 Agent 未协调同时改同一文件或公共接口；契约变更需评估影响并通知依赖方。
- 所有 Agent 必须提交实际差异、测试结果、已知问题、剩余风险；不得口头宣布完成。
- 主控依据自动化、接口、权限、端到端测试决定验收。

## 十、最终执行原则

1. 主控统一规则，但不能成为瓶颈；专业 Agent 在边界内自主完成。
2. 专业 Agent 可并行，但系统只能按统一契约集成；并行不牺牲接口一致性。
3. 交付以证据为准，不以自评为准；代码存在、测试执行、测试通过、真实业务可用是四个不同层次。
