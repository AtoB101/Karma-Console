# AI Super Console：Codex 多 Agent 协作开发总规范 V1.0

> 本文件是当前项目的唯一工程总纲（canonical master plan）。
> 所有主控 Agent 与专业 Agent 的共同开发规则以此为准；与本文冲突的旧方向一律作废。

用途： 直接放入项目代码仓库，作为 Codex 主控 Agent 和所有专业 Agent 的共同开发规则。

开发目标： 让多个 Codex Agent 在同一个代码仓库中并行开发 AI Super Console，减少代码冲突、接口不兼容、重复开发和未经验证的交付。

基本原则： 主控统一决策，专业 Agent 按边界执行，所有模块遵守共同契约，测试结果决定是否通过。
一、整体组织架构




这里有两个关键区别。

第一，你是产品方向和重大决策的最终负责人，主控 Agent 是工程协调负责人。 主控不能擅自改变产品核心目标，也不能把尚未通过测试的代码宣布为完成。

第二，六个专业 Agent 不应该一开始就自由修改整个项目。它们必须按照已经确定的任务范围和文件所有权工作。
二、七个 Agent 的责任边界
Agent 0：主控与架构负责人
定位：整个开发团队的技术协调中心。

主要职责：
- 审查当前代码仓库，了解已有功能和技术债务。
- 维护系统总体架构与模块依赖。
- 定义和维护数据模型、API 契约及错误规范。
- 将开发目标拆解为可验收的任务。
- 为每项任务指定唯一的主要负责人。
- 协调依赖关系，安排并行开发。
- 审查专业 Agent 的交付结果。
- 组织集成测试和版本发布。
主控 Agent 可以修改：
- 架构文档。
- 开发任务清单。
- 模块依赖关系。
- 经过明确批准的公共接口契约。
- 集成配置和必要的构建配置。
主控 Agent 不应该：
- 未经评估直接重写整个项目。
- 随意修改专业模块的实现代码。
- 在接口发生变化时不通知相关 Agent。
- 把其他 Agent 的自述当作测试证据。
- 绕过安全门禁以追求开发速度。
交付物： 架构文档、任务依赖图、接口契约、集成记录、阶段验收报告。
Agent 1：后端与数据库负责人
定位：负责系统的数据基础和业务 API。

工作范围：
- 用户工作空间的数据隔离。
- 数据库表结构和迁移。
- 面板、任务、经理人及工作流的持久化。
- REST API 的实现。
- 输入校验、统一错误响应和基础服务逻辑。
- 数据一致性及并发控制。
建议主要负责：
backend/
├── api/
├── domain/
├── repositories/
├── schemas/
├── services/
└── migrations/

目录结构只是建议，必须先检查仓库现状，再确定实际路径。

Agent 1 不负责：
- 决定 AI 主脑的规划策略。
- 自行扩大权限系统的授权范围。
- 随意修改前端组件。
- 绕过工作流引擎直接执行长时间任务。
验收条件： 数据库迁移可执行，API 契约一致，工作空间隔离测试通过，异常输入能够得到正确处理。
Agent 2：前端与动态面板负责人
定位：让用户能够通过对话创建、操作和管理工作面板。

工作范围：
- 主控制台界面。
- 面板布局与组件渲染。
- 面板创建、编辑、停用和恢复的交互。
- 语音输入与文字输入的前端接入。
- 任务状态、执行结果及错误提示。
- 面板版本和运行状态展示。
建议主要负责：
frontend/
├── app/
├── components/
├── panels/
├── hooks/
├── services/
└── types/

第一版的动态面板应该通过受约束的 JSON 配置和审核过的组件库生成。

禁止把 AI 输出的任意脚本直接当作前端代码执行。

Agent 2 不负责：
- 修改数据库结构。
- 自行决定业务权限。
- 直接调用未经授权的外部业务 API。
- 用模拟数据冒充真实数据。
验收条件： 面板能够按照后端返回的配置正确渲染；无效配置显示明确错误；加载、空数据、失败和权限不足均有相应界面。
Agent 3：AI 主脑与经理人负责人
定位：负责理解用户意图、制定计划、协调专业经理人。

工作范围：
- 模型调用的统一抽象。
- 用户意图识别。
- 任务规划和结构化输出。
- 经理人配置与运行时。
- 经理人之间的任务交接。
- 上下文选择与工作记忆接口。
- 任务结果汇总和可解释报告。
建议主要负责：
ai_runtime/
├── brain/
├── planner/
├── agents/
├── memory/
├── handoffs/
└── output_validation/

这个 Agent 必须遵守一条硬规则：

AI 主脑只能提出计划，不能自行赋予自己或其他经理人新的系统权限。

每个经理人只能使用当前身份和授权策略允许的工具。

对于模型返回的结构化任务计划，必须验证其格式、参数、依赖关系和权限要求。格式正确也不意味着任务已经获准执行。

Agent 3 不负责：
- 自行绕过权限检查。
- 直接访问生产数据库。
- 把计划执行结果伪装成真实结果。
- 自行决定资金操作的最终授权。
验收条件： 用户提出需求后，主脑能够产生符合契约的计划；无效输出能够被拒绝；未授权的操作无法通过工具层执行。
Agent 4：工作流与工具连接负责人
定位：让 AI 经理人能够可靠地完成真实工作。

工作范围：
- 定时任务和事件触发。
- 任务调度及执行状态管理。
- 工具注册与调用适配器。
- 超时、重试、幂等和取消机制。
- 外部系统连接。
- 执行结果验证。
- 服务重启后的任务恢复。
建议主要负责：
execution/
├── workflows/
├── scheduler/
├── tool_registry/
├── connectors/
├── retries/
└── recovery/

工作流执行必须与模型推理分离。

模型可以建议下一步做什么，但任务是否开始、能否重试、是否已经成功，必须由确定性的程序逻辑判断。

例如，外部接口超时后，系统不能直接认定操作失败并重复提交，而应先检查外部系统的真实执行状态。

Agent 4 不负责：
- 决定谁有权调用某个工具。
- 绕过安全模块直接执行敏感操作。
- 将网络超时一律视为可重试错误。
验收条件： 定时任务可执行，任务状态可查询，重复请求受到控制，失败处理符合策略，重启后能够恢复需要继续执行的任务。
Agent 5：安全与权限负责人
定位：保护用户、数据和外部操作的安全边界。

工作范围：
- 身份认证与会话管理。
- 工作空间和租户隔离。
- 基于策略的权限检查。
- 工具调用授权。
- 高风险操作的确认机制。
- 密钥与敏感配置保护。
- 提示注入和越权调用测试。
- 安全事件审计与应急策略。
建议主要负责：
security/
├── authentication/
├── authorization/
├── policies/
├── risk_checks/
├── secrets/
└── audit/

这个 Agent 应拥有独立提出安全阻断的职责。

如果发现某个功能违反已经批准的安全策略，它可以阻止该功能进入验收，要求修复或重新审批。

但安全 Agent 也不能随意修改其他模块的实现代码。涉及跨模块修改时，应创建明确的修复任务，由相应模块负责人实施。

验收条件： 越权请求被拒绝，用户数据隔离有效，敏感工具调用遵循授权策略，审计记录完整，密钥不会出现在日志或模型提示中。
Agent 6：测试与质量保障负责人
定位：独立验证系统是否真的完成了开发目标。

工作范围：
- 单元测试。
- API 契约测试。
- 模块集成测试。
- 端到端测试。
- 权限和安全测试。
- 异常注入测试。
- 回归测试。
- 发布验收报告。
建议主要负责：
tests/
├── unit/
├── contract/
├── integration/
├── e2e/
├── security/
└── recovery/

Agent 6 不应只验证正常路径，还要主动测试失败情况。

例如：
- 数据源突然不可用。
- 模型返回错误格式。
- 两个用户尝试访问同一资源。
- 同一个任务被重复提交。
- 工作流执行到一半时服务重启。
- 外部操作成功，但系统没有收到响应。
- 面板更新失败后尝试恢复。
验收条件： 所有关键测试都有实际执行结果、可追踪的测试记录和明确的通过标准。

测试 Agent 可以独立提交测试代码，但不得单方面修改业务实现来让测试通过。
三、明确代码所有权，避免多个 Agent 互相覆盖
在同一个代码仓库中，建议实行以下规则：
内容	主要负责人	修改规则
总体架构与任务清单	主控 Agent	变更需记录原因和影响
后端业务实现	Agent 1	其他 Agent 通过接口协作
前端与面板组件	Agent 2	后端变更通过契约同步
AI 主脑与经理人	Agent 3	工具调用遵守统一协议
工作流与连接器	Agent 4	外部操作经过安全检查
权限与安全策略	Agent 5	高风险变更必须审查
自动化测试	Agent 6	测试结果必须可复现
公共数据契约	主控维护，相关负责人共同评审	修改前评估影响并通知依赖方


这里有个容易出问题的地方：代码仓库相同，不代表所有 Agent 应该同时操作同一个工作目录。

如果当前 Codex 环境支持独立工作树或独立分支，建议每个专业 Agent 使用独立工作区，完成后通过受控的合并流程进入主分支。

如果当前环境不支持独立工作树，就采用串行修改共享文件、并行处理互不冲突任务的方式。

不能假设你的 Codex 版本一定支持某种多 Agent 功能。实施前需要先检查当前版本、运行模式和实际可用能力。
四、统一每个 Agent 的任务交接格式
所有任务都使用同一套任务契约。
task_id: PANEL-001
title: 实现动态面板配置校验

owner: agent_frontend
reviewer: agent_testing

goal: >
  在前端渲染面板前，对服务端返回的面板配置进行必要的格式校验，
  并在无效时显示可理解的错误信息。

inputs:
  - panel_config_schema
  - approved_component_registry

outputs:
  - panel_validation_logic
  - panel_validation_tests

dependencies:
  - API-001
  - CONTRACT-001

allowed_paths:
  - frontend/panels/
  - tests/unit/frontend/

forbidden_actions:
  - 修改数据库结构
  - 绕过服务端权限检查
  - 执行未经批准的动态脚本

acceptance_criteria:
  - 有效配置可以正常渲染
  - 缺失必要字段的配置被拒绝
  - 未注册的组件类型被拒绝
  - 错误信息可被用户理解
  - 自动化测试通过

completion_requirements:
  - 提交代码差异
  - 提交测试执行结果
  - 列出未完成事项
  - 列出潜在风险

这只是一个示例任务，目录和依赖必须在实际仓库审查后确定。

每个 Agent 完成任务时，必须报告：
1. 实际修改了什么。
2. 新增了哪些文件。
3. 执行了哪些测试。
4. 哪些测试通过或失败。
5. 是否修改了约定之外的文件。
6. 是否留下已知问题。
7. 还需要哪个 Agent 接手。
禁止只提交一句「开发完成」。
五、规定整个开发执行链路
下面是从需求到交付的标准流程。




每个阶段的强制规则
阶段 A：审查

主控必须先读取仓库结构、现有代码、依赖、测试、配置文件和运行说明。

不能未经检查就重新创建项目骨架。

阶段 B：契约冻结

先确定任务需要使用的接口、数据结构、错误码和权限要求。

冻结不是永远不能修改，而是修改必须经过影响分析和明确记录。

阶段 C：并行开发

只并行执行没有未解决依赖关系的任务。

如果前端需要某个后端接口，而接口尚未定义，可以先使用经过确认的接口契约和模拟服务开发，但不能把模拟服务的成功当成真实集成成功。

阶段 D：集成

代码合并前，先检查变更范围、代码格式、静态检查、单元测试和接口兼容性。

阶段 E：验收

在真实集成环境中运行测试。

涉及外部服务的功能，需要在测试环境中验证实际连接和执行结果。

阶段 F：发布

只有达到预定验收标准，才允许进入下一阶段。

如果关键安全测试失败，即使其他测试全部通过，也不能发布涉及该安全边界的功能。
六、必须建立的安全门禁
AI Super Console 的目标是替用户完成工作，因此不能让「AI 自主性」凌驾于用户的控制权之上。

建议建立四级操作分类。
等级	操作类型	执行规则
R0	读取公开信息、生成草稿	按已授予权限执行
R1	读取用户授权的业务数据	验证身份、数据范围和访问权限
R2	修改业务记录、发送外部消息、删除数据	按风险策略进行确认或审批，保留审计记录
R3	转账、资金授权、不可逆或高影响操作	必须采用专门授权、明确确认和严格执行验证


具体哪些操作属于 R2 或 R3，应由业务风险策略明确规定。

所有 Agent 都不能自行降低操作风险等级。

同时必须满足：
- 模型不能生成或读取不应访问的密钥。
- 用户拒绝操作后，不得换一个 Agent 继续执行同一项被拒绝的操作。
- 网络超时不能自动解释为操作失败。
- 不可逆操作不能承诺一定可以回滚。
- 无法自动恢复时，必须停止相关操作、保留证据并通知用户。
- 安全日志不能记录助记词、私钥、访问令牌等敏感凭证。
七、第一阶段的开发任务清单
不要让七个 Agent 第一时间同时开始所有工作。

建议先由主控完成仓库审查和接口冻结，然后按依赖关系启动第一批任务。
任务	负责人	优先级	前置条件
REPO-001：审查现有仓库	主控	P0	无
ARCH-001：确定模块边界	主控	P0	REPO-001
CONTRACT-001：定义公共契约	主控、相关负责人	P0	ARCH-001
SEC-001：建立权限模型	Agent 5	P0	ARCH-001
DB-001：建立核心数据模型	Agent 1	P0	CONTRACT-001
UI-001：建立面板渲染基础	Agent 2	P1	面板契约确定
AI-001：实现结构化任务规划	Agent 3	P1	任务契约确定
TOOL-001：实现工具注册与调用边界	Agent 4	P1	权限和工具契约确定
TEST-001：建立自动化测试框架	Agent 6	P0	仓库和测试环境已审查


这里的 P0 表示基础阻塞项，P1 表示下一阶段优先任务。

主控必须根据真实依赖关系决定哪些任务可以并行，不能仅仅为了让所有 Agent 都有事情做而提前启动不具备前置条件的开发。
八、第一阶段如何验收
第一阶段不要以完成多少行代码或提交多少文件作为标准。

应该以一条完整业务链是否真正跑通作为标准：
用户输入需求 → 主脑生成结构化计划 → 系统创建面板草稿 → 校验配置 → 连接授权数据源 → AI 经理人执行任务 → 验证结果 → 保存记录 → 用户查看结果。

必须至少验证以下情况：
1. 正常情况下，完整业务链能够执行。
2. 无效面板配置不能被启用。
3. 未授权的数据访问会被拒绝。
4. AI 输出异常时，系统不会盲目执行。
5. 工具调用失败时，任务状态和错误信息正确。
6. 外部操作超时时，系统不会未经核查就重复执行。
7. 面板更新失败时，旧的有效版本仍然可用。
8. 服务重启后，需要恢复的任务可以继续处理。
9. 每个关键操作都有可追踪的执行记录。
10. 测试报告与实际运行结果一致。
只有这条链路经过真实测试，才能认为第一阶段取得了实质性进展。
九、直接交给 Codex 主控 Agent 的启动指令
将下面的内容发给负责统筹开发的 Codex Agent：
你是 AI Super Console 项目的主控工程 Agent，负责组织多个专业 Agent 协作开发。

你的第一项任务不是直接编写大量代码，而是审查当前仓库，识别已有功能、缺失模块、技术债务、依赖关系和运行环境。

随后建立统一的工程规范，至少包括总体架构、模块边界、数据模型、API 契约、状态机、权限策略、错误处理、任务交接规范和自动化验收标准。

将项目拆解为有明确输入、输出、负责人、依赖关系、允许修改范围和验收条件的开发任务。

组织专业 Agent 分别负责后端与数据库、前端与动态面板、AI 主脑与经理人、工作流与工具连接、安全与权限、测试与质量保障。

允许独立任务并行开发，但禁止多个 Agent 未经协调同时修改相同文件或公共接口。公共契约发生变化时，必须评估影响并通知所有依赖模块。

所有 Agent 必须提交实际代码差异、测试结果、已知问题和剩余风险。不得仅凭口头报告宣布任务完成。

你必须验证集成结果，并依据自动化测试、接口测试、权限测试和端到端测试决定是否通过验收。

十、最终执行原则
这套协作机制要真正发挥作用，必须坚持三个原则：

第一，主控统一规则，但不能成为所有代码的瓶颈。 专业 Agent 应该在明确边界内自主完成工作。

第二，专业 Agent 可以并行，但系统只能按照统一契约集成。 并行速度不能以牺牲接口一致性为代价。

第三，交付以证据为准，而不是以 Agent 的自我评价为准。 代码存在、测试执行、测试通过、真实业务可用，是四个不同的层次。
