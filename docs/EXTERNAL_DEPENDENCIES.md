# 外部依赖登记清单（External Dependencies Register）

> 用途：集中登记所有**本地代码无法独立验证、需要外部凭证/平台/法务/基础设施条件**才能完成的事项。
> 原则：只登记真实状态，**不伪造联调完成**。本地已完成的是接口、协议对齐、stub 与确定性测试；
> 下列每一项在外部条件就绪前，验收一律按"未联调 / 待外部"处理，不得计入已交付能力。
>
> 最后更新：P31（新增第 8 节 MCP 与主流 Agent 工具接入路线与安全边界）。

## 状态图例

- `未联调`：本地仅完成接口/协议对齐与 stub 测试，未对真实外部系统发起成功调用。
- `待外部`：需要对方平台凭证、审核、法务或基础设施到位后才能验证。
- `本地已就绪`：请求构造、协议字段、错误分类、stub 闭环已在代码与测试中落地。

**接入安全边界（落地 MCP/第三方工具时必须遵守）**：
1. 工具一律经统一网关执行，模型只产出计划，不得直连外部；
2. 默认仅公网 https，私网/本地/重绑定地址阻断（沿用 `validate_url`/`recheck_url`）；
3. 写操作按 R 级风险分级，R3+ 需 owner 审批；凭证存服务端、不下发前端；
4. 第三方工具先过模块审核与配置沙箱，再按白名单挂载，禁止任意代码执行；
5. 每次调用记审计与执行结果核验，失败按分类重试/补偿/停止。

**技术边界（诚实说明）**：对称 at-rest 加密保证"库文件丢失不泄露"，但持密钥的部署方仍可解密；要做到"平台本身无法知道"必须把密钥留在客户端（owner 口令派生、服务端只存密文），并牺牲部分服务端检索/聚合能力；零知识证明需独立电路与 setup，不能用普通哈希链替代。三者分属不同密码学目标，落地前需按威胁模型单独设计。

> Owner-only E2EE 的威胁模型、拍板字段、Passkey 解锁、虚拟号与备份路线已整理为拍板版设计：`docs/E2EE_DESIGN.md`（E2EE 客户端加密未实现，仅设计与已落地部分）。运营商隐私号、声纹、S3/WebDAV 备份、zkSNARK 均为外部项，本地不伪造接通或证明。

## 登记规则

1. 任何一项取得真实联调证据后，在此更新为已验证，并附测试/日志/回执链接；不得先改状态后补证据。
2. 本地 stub、确定性测试、协议对齐**不计入**外部联调完成。
3. 上线门槛（`docs/LAUNCH_GATE.md`）中涉及上述项的，在对应外部条件就绪前保持阻断。
